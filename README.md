# SPOT Next.js + DatoCMS starter

Starting point for SPOT client projects on Next.js + DatoCMS. Forked from
[datocms/nextjs-starter-kit](https://github.com/datocms/nextjs-starter-kit), paired with the
DatoCMS template project **SPOT Starter Next** (project id `225924`).

## Starting a new client project

1. Open `https://dashboard.datocms.com/deploy?repo=gawema/spot-nextjs-datocms-starter:main`.
   Name the project after the client and create it under the SPOT organization.
2. Choose Vercel when asked for hosting. The flow creates the CDA/CMA tokens, injects them
   as env vars, and calls `/api/post-deploy` to register the cache-invalidation webhook.
3. The repo you get is a private **copy, not a fork**, so it shares no history with this
   base. If you want to be able to pull base updates later, link it right away, before the
   first edit, while both trees are still identical:

   ```bash
   git remote add base https://github.com/gawema/spot-nextjs-datocms-starter.git
   git fetch base
   git merge base/main --allow-unrelated-histories
   ```

   Done at this point the merge is conflict-free. Done later, after the project has
   diverged, it is a fight.

4. Set `NEXT_PUBLIC_SITE_URL` and the locales for the project, then delete what the client
   does not need. Deleting is cheaper and safer than generating.

## What is inside

Three layers. Keep them apart in your head:

- **Upstream** (`src/lib/datocms`, `src/app/api`, the gql.tada wiring). Do not edit these
  in place. Wrap them instead, so updates from the DatoCMS starter kit stay mergeable.
- **SPOT layer**: i18n and locale routing, the fluid design-token generator, animation
  hooks, media wrappers, SEO helpers, debug components.
- **Example section**: one section component that demonstrates the convention. Copy it,
  then delete it.

## Conventions

- **Sections and blocks**: every component owns its colocated `fragment.ts`. Pages render
  by switching on `__typename` in the section registry. Add a section in one place, not four.
- **Design tokens**: never hand-edit `src/app/tokens/fluid.css`. Change
  `scripts/generate-fluid-tokens.mjs` and run `npm run generate-fluid-tokens`.
- **Never call DatoCMS from the proxy/middleware.** It runs on every request and does not
  use the Next.js Data Cache, so `force-cache` and `next.tags` are silently ignored. This
  has already caused a real API overage on another project.
- **After any schema change**: `npm run generate-schema` and `npm run generate-cma-types`.
  Both also run in `prepare`, so a schema/env mismatch fails the build rather than
  breaking at runtime.

## CMS side

Cloning the template brings the schema and the base content (layout record, navigation,
translation keys). `migrations/` holds the autogenerated seed snapshot of that schema: it is
there for code review and to rebuild from a blank project if the template drifts. Note that
plugin appearance addons carry per-project ids and do not survive migrations, so
plugin-driven field UI is configured in the CMS, not in a migration.

## Environment variables

Copy `.env.local.example` to `.env.local` and fill it from the project's API tokens page.
`DATOCMS_ENVIRONMENT` is optional and points the whole app at a sandbox environment.

## Pulling updates from the DatoCMS starter kit

The `upstream` remote points at `datocms/nextjs-starter-kit` and the histories are joined,
so their changes can be reviewed and merged directly:

```bash
git fetch upstream && git log --oneline HEAD..upstream/main
```

```bash
git merge upstream/main
```

Conflicts appear only in the files we deliberately changed. Today that is `README.md`,
`datocms.json`, the home page title, and the `DATOCMS_ENVIRONMENT` support in
`executeQuery.ts`; `git diff upstream/main -- src` prints the full list at any time. Keep
ours in those, take theirs everywhere else, and never let a security fix sit unmerged.

## Sending an improvement back to this base

Keep the improvement in its own commit, touching only shared files. Then from here:

```bash
git fetch client
git cherry-pick <sha>
```

A commit that mixes shared and client-specific changes will conflict on cherry-pick,
because the client-only files do not exist in this repo. That is why the commits stay clean.

Anything with a client name, a brand colour, or a client content model in it does not belong
here. If it is useful but hardcoded, make the hardcoded part a parameter and then bring it up.

## Verification

`npm run lint` can break under Next 16. The reliable pair is:

```bash
npx tsc --noEmit && npx prettier --check .
```
